# CLAUDE.md

## Purpose

sqldta is a Stata package (Stata 16 or later) that loads a table from Microsoft SQL Server into a Stata frame over ODBC and applies value labels, variable labels, display formats, variable notes, dataset notes and a data label from a label table of a documented layout. It is generic and public, at github.com/w4rhol/sqldta, under the MIT licence (decided 18 Oct 2026; the copyright is the maintainer's, confirmed 21 Oct 2026). It replaced an internal predecessor at the site where it was first written; the predecessor's code is not in this repository. Maintainer: Warren Holroyd (w4rhol).

## Design decisions

Each item is settled unless the maintainer reopens it. Rationale is given so you can tell when a proposed change would break it.

**One command.** `sqldta` replaced several internal commands at the site where it was first written. Syntax:

```
sqldta [if], database(name) dataset([schema.]table) [server(name) frame(name) clear
        lowercase nodecformat labels(types) labeltable([schema.]table) sqlselect(list)
        sqlwhere(clause) sqlrand(#) unicode(list)]
sqldta settings [, server(name)]
```

`sqldta settings` (added 21 Oct 2026, when the maintainer said to proceed with the proposals for the settings) shows the settings file read, each setting and where it comes from, and, for `server()` or else the first of `SQLDTA_SERVERS`, tries every connection template and shows its return code and time; it returns them in r() (see Site configuration). The word `settings` as the first word is otherwise a syntax error, so it does not clash with a load.

Decided 18 Oct 2026, when the maintainer agreed to depart from the predecessor's options for a shorter syntax that the dialog can build: `labels(types)` replaces `vallabels varlabels varnotes dtanotes`; `dataset()` takes the schema, replacing `dataschema()`; `labeltable()` takes the schema, replacing `labelschema()`; and `multischema()` is dropped (see Split tables). Minimum abbreviations: `datab`, `datas`, `ser`, `fra`, `low`, `nodec`, `labels` in full, `labelt`, `sqls`, `sqlw`, `sqlr` and `uni`. `server()` defaults to the first word of `$SQLDTA_SERVERS` and is required only when that global is unset. `dataset()` and `labeltable()` are split at the dot: a name with more than one dot or an empty part stops with error 198, so a schema or table whose name contains a dot cannot be named. A table named without a schema is in `$SQLDTA_DATASCHEMA`, or `dbo`; a label table named without one is in the schema of the default label table (see Site configuration). The options of the earlier syntax (`dataschema()`, `labelschema()`, `multischema()`, `vallabels`, `varlabels`, `varnotes` and `dtanotes`) stop with error 198. The `if` qualifier is new (see Filtering), as are `clear`, `nodecformat` and `unicode()` (decided 20 Oct 2026; see Data types).

`labels(types)`: `all` (the default), `none`, or any of the words `values` (ValueLabel rows), `variables` (VariableLabel), `formats` (Format), `varnotes` (VariableNote), `dtanotes` (DatasetNote) and `datalabel` (DataLabel), in any case and order; another word, or `all` or `none` with other words, stops with error 198. The maintainer chose these Stata-like words over the names of the label types, and chose labels by default (both 18 Oct 2026). Each PropertyType has its own word, which settles how Format and DataLabel rows pair with the label options.

**Site configuration by a settings file and globals.** Decided 21 Oct 2026, when the maintainer raised that a user's script may legitimately run `macro drop _all`, which removes global macros, after which the package no longer works as the site set it up (`clear all` does not remove globals: the manual entry for `clear` lists what it removes, and globals are not among them), and chose a configuration file. Each setting is the option, where there is one, else the global of its name if that is set, else the line of that name in the settings file, else the built-in default. The settings file is the first file named `sqldta_site.cfg` along the ado-path (`findfile`), which includes the current directory, so a project folder can hold its own. It is read on every call of `sqldta`, and on every action of the dialog's helper, by `_sqldta_settings.ado` (its own file, because sqldta, the helper and `_sqldta_odbc` use it), so nothing in memory needs to survive. Each line is a setting's name (the global's name, in any case), a space or a tab, and the value; blank lines and lines that begin with `*` or `//` are passed over; a UTF-8 byte-order mark and carriage returns are allowed; a line with another name is passed over with a note (not in the dialog), and its number is in `r(ignored)` of `_sqldta_settings`; `SQLDTA_CONNECTION` may be given on several lines (see Connection); for the others a later line replaces an earlier one. Values are read in Mata, so `$` and backquotes in them are kept. The package installs an example of the file, `src/sqldta_site_example.cfg`, the only copy in the repository, with every setting and a comment on each (decided 21 Oct 2026, when the maintainer asked that `net install` install it, so that users need not download it separately). It is listed in `sqldta.pkg` with `F`, not `f`, because [R] net says that an `f` file is installed according to its suffix and gives a `.dta` file going to the current directory as an ancillary file, without listing the suffixes, while `F` always copies to the system directories. Its name has no leading underscore, so that it goes to the letter folder `s`, where a copy renamed in place to `sqldta_site.cfg` is found, since `findfile` searches the letter subfolders of each folder on the path unless `nodescend` is given ([P] findfile). Local runs of `net install` at archive 37e355f (21 Oct 2026) put it in `s` with no complaint; a copy renamed there was found and read; `ado update` left the copy as it was and put the example back; and `ado uninstall` removed the package's files and left the copy (archive HANDOVER.md, section 4.16). No program in `src/` names the example, so an installed example never takes effect as settings; a site copies it as `sqldta_site.cfg` to SITE or a shared PERSONAL folder, and a single user may copy or rename it in place. Patterns seen in other packages, from their source (21 Oct 2026): globals in `profile.do` (common, and lost to `macro drop _all`); a file found along the ado-path and read on each call (estout's `estout_<style>.def`, whereis's `whereis.dir`); and a site ado-file of globals that the package runs on each call (weaver's `weaversetup.ado`). A settings ado-file run when a marker global is empty was also proposed and not taken. The settings and globals are:

```
SQLDTA_SERVERS       space-separated server names; first is the default
SQLDTA_DATABASES     space-separated database names offered in the dialog, for every server
SQLDTA_DEFAULTDB     the database the dialog selects first: space-separated words, each a
                     database for every server, or server=database for one server
SQLDTA_DLGREMEMBER   anything other than empty or 0 makes the dialog reopen at the server
                     used last, and at the database and schema chosen last on each server,
                     in the same session
SQLDTA_DATASCHEMA    schema of a table named in dataset() without one; default dbo
SQLDTA_LABELTABLE    default label table, as schema.table, or table, which is then in ref;
                     default ref.DataProperties
SQLDTA_CONNECTION    ODBC connection-string template; %server% and %database% are replaced by
                     the server and database names; in the settings file, several lines,
                     tried in order; dsn means the ODBC data source named after the server
SQLDTA_DTTEXT        anything other than empty or 0 loads date-time columns by the earlier
                     method, text converted with clock(); a fallback for production
```

Rationale for keeping the globals: a global replaces a setting for a session or a do-file, the tests set them, and `dsn` in `SQLDTA_CONNECTION` forces the data source whatever the file lists (the tests use it, with an empty settings file of their own first on the ado-path). The maintainer asked on 21 Oct 2026 to keep as many settings as possible available in the file, `SQLDTA_DTTEXT` included. No other globals are used anywhere in the package; the Mata external variables are `_sqldta_conn` (see Connection) and the dialog helper's three, described under Dialog. `sqldta` returns the settings file read in `r(settings)`. `SQLDTA_DTTEXT` was added on 20 Oct 2026, when the maintainer chose a site global over an option on each call, so that one line in the site setup reverts every user's loads if a problem appears with date-times sent as numbers. `SQLDTA_DEFAULTDB` was added on 20 Oct 2026, when the maintainer asked for a default database, as the earlier dialog had, with a default for each of several servers; its name says that it is a default (the maintainer's choice over `SQLDTA_DATABASE`, one letter from `SQLDTA_DATABASES`). The dialog alone reads it: `database()` stays required, and the dialog always writes it. `SQLDTA_DLGREMEMBER` was added the same day: the maintainer did not need the dialog to reopen at the database and schema chosen last, but asked for it as a site option, and then for it to reopen at the server used last as well.

**Connection.** The connection is a template, in which the package replaces each `%server%` with the server name and each `%database%` with the database name, and connects with `connectionstring()`, or the word `dsn`, or nothing, either of which means `dsn("<server>")`. The template is the global `SQLDTA_CONNECTION` if it is set, used as it is; otherwise the `SQLDTA_CONNECTION` lines of the settings file. One line is used as it is. Several are tried in order with `SELECT 1` (decided 21 Oct 2026, when the maintainer chose a list of drivers in the configuration, tried in order, over finding the installed drivers through the registry, which needs the shell and ties the package to Windows, and asked that it not be done on every call): `_sqldta_settings, connect`, which sqldta calls once at the start of each load, tries them the first time a server is used in a session, and keeps the first that connects, with the list it came from, in the Mata external variable `_sqldta_conn`, one row for each server; later calls use it without trying, and try again only when the list changes, after `clear mata` or `clear all`, or if none connected. `_sqldta_odbc` takes the global if set, otherwise the connection kept for its server, otherwise has `_sqldta_settings` choose one, so the file is not read for each query. When the template used is not the first, a note names its driver (the maintainer asked for a warning when a fallback driver is used, 21 Oct 2026); the package knows nothing about drivers, so the warning follows from the order, the preferred first. When none connects, a note says so and the data source is used, and nothing is kept as chosen. The attempts call `odbc load` directly and quietly, the one exception to `_sqldta_odbc`, because their failures are expected. All queries fully qualify objects as `[database].[schema].[table]`, so the package itself needs no database in the connection. The `%database%` token is optional: a site that adds `Database=%database%;` makes unqualified object names in `sqlwhere()`, such as a subquery on another table, resolve in `database()` rather than in the login's default database; the attempts put the database of the load there, or master. Choosing and ordering the drivers is the site's: src/sqldta_site_example.cfg lists ODBC Driver 18 (with `TrustServerCertificate=yes`), ODBC Driver 17, ODBC Driver 13, SQL Server Native Client 11.0 and the "SQL Server" driver, the last three as fallbacks because, the maintainer said on 21 Oct 2026, they are still on many corporate laptops. Driver 17 and earlier do not encrypt by default (`Encrypt=no`; Microsoft's documentation, read 21 Oct 2026), so their templates need no encryption attributes to connect; a site that wants them to encrypt adds `Encrypt=yes;TrustServerCertificate=yes;`. Microsoft has released no ODBC Driver 19 (the current versions are 18.7.1.1 and 17.11.1.1); a later driver works as soon as a template names it. The example value, used in the help file's connection paragraph, is `Driver={ODBC Driver 18 for SQL Server};Server=%server%;Trusted_Connection=yes;TrustServerCertificate=yes;`. The help file has one paragraph on Driver 18: it encrypts by default and rejects a server certificate that the client does not trust unless `TrustServerCertificate=yes` is set. With a server certificate that the client does not trust, Driver 18 connects only with that attribute, and Driver 13, Native Client 11.0 and the legacy "SQL Server" driver connect without it (the maintainer's tests). The whole test suite passed through Driver 18, Driver 13 and Native Client 11.0 as the template, with the same results (archive logs of 2880551), and through the legacy driver as the DSN. A single template, from the global or one line of the file, is used without an attempt, so a template that cannot connect stops the load with the driver's message; sqldta falls back on the data source only from a list of several. An attempt to a server that does not answer waits for the login time-out, 15 s by default (the maintainer's run of 21 Oct 2026), and a driver that is not installed fails at once. Rationale: every driver attribute is a site decision, so the package never needs to know any driver's defaults, and no per-user DSN named after each server is required.

**Frames.** Working frames use names from `tempname`, which Stata drops automatically when the program ends. Data loads into `frame()` if given (created if absent), otherwise into the current frame. If the target frame already holds data and `clear` was not specified, exit with error 4. With `clear`, an existing target frame is cleared with `frame <name>: clear` just before the data query, after every check that can stop the command, because `odbc load` ignores a `clear` written after a very long `exec()`, and stops with r(18), "you must start with an empty dataset" (seen on 19 Oct 2026 for wide tables, whose queries are long, and reproduced by the clear report of the log of archive 46d4e17 with a query of 43,055 characters, where `clear` written before `exec()` worked); if the data query then fails, the frame is left empty, which the help file says. The message is Stata's own and varies by version; Stata 19 prints "no; dataset in memory has changed since last saved". A frame holds data if it has any variables or observations; this is stricter than `use`, which refuses only when the data have changed since they were last saved. `sqldta` never changes the current frame; the dialog emits `frame change` when its "switch to frame" box is ticked. Rationale: matches the conventions of `use` and `frame put`; explicit over implicit.

**Loading.** The queries run in this order: the label-table check and its Link rows, the column query, the key check of each linked table, the data query, and the label query. The target frame is created, when it does not exist, just before the data query, so an error in an earlier step leaves no frame behind. Build the SQL incrementally: the column list is `*` unless `sqlselect()` is given, the table has columns whose names are not valid Stata names, or a column loaded has a type that is sent as an expression (see Data types); a `WHERE` clause is appended only if the `if` qualifier or `sqlwhere()` is given, each part in parentheses and joined by AND; `sqlrand(N)` produces `SELECT TOP (N) ... ORDER BY NEWID()`, which is a true random sample at the cost of a full scan (document this in the help). Every SQL string is built and passed in compound double quotes. Every `odbc load` of a query goes through one subprogram, `_sqldta_odbc`, which is in its own file, `_sqldta_odbc.ado`, because the dialog helper uses it too; it runs `odbc load` under `capture noisily` so that the driver's message is shown, and on failure prints the server, database, object and connection (the driver its template names, or the data source). The connection attempts of `_sqldta_settings` are the exception (see Connection). A failure of the data query, the column query or the Link-row query stops the command with `exit _rc`, after dropping the target frame if `sqldta` created it, because without them the loaded data could be incomplete; a failure of the label query displays a note and the command continues. Test strings for emptiness with ``"`x'"' == ""`` (compound quotes), never `missing()`.

**Labels.** Fetched after the data load, into a tempname frame, with one `SELECT DISTINCT` for all requested label types of the dataset and of its linked tables, each selected by its schema and name (TableSchema and TableName); rows with empty PropertyText are excluded. DataType is not read (decided 19 Oct 2026, because the maintainer found it redundant and sometimes wrong, while the type of the loaded variable is exact): ValueLabel rows are applied to variables that are numeric once loaded, and ValueLabel rows for a variable that is a string in Stata, which cannot take value labels, are passed over and not counted as skipped, like rows for columns not selected. The predecessor, and sqldta before that date, applied only value-label rows whose DataType was INT. `labels()` gives the PropertyTypes fetched, every type by default. The label table is optional metadata: the package first checks it with `OBJECT_ID()`, and if it is missing or unreadable continues without labels, and the summary line says that the label table was not found, with no separate note, so that a site without a label table sees no extra line (decided 18 Oct 2026); the same check, one query, confirms through `[database].sys.all_columns` that the label table has the six columns of the layout (see Metadata contract), and if any is missing, a note names them and the command continues without labels and without following Link rows, with `r(labelstatus)` failed and the summary line saying that the label table lacks columns of its layout (decided 21 Oct 2026); if the label query itself fails it displays a note and continues. Only the data load is a hard error. Each row's ColumnName is matched to a loaded variable without regard to case; a row with no match is skipped, and skipped rows are counted in the end-of-run summary as set out under Column selection, so that errors in the metadata are visible. Loaded variable names stay as the user typed them in `sqlselect()`, which is what the predecessor did, and which the test log of 17 Oct 2026 confirmed with ODBC Driver 18; `lowercase` renames every variable with `rename *, lower` before labels are applied. Rows are applied, in their order, by running in the target frame via the `frame <name>:` prefix and under `capture`: ``label define <var> <PropertyCode> `"<PropertyText>"', modify`` for ValueLabel rows with an integer code (then `label values <var> <var>` once per variable), `label variable` for VariableLabel rows, `format <var> <fmt>` for Format rows once `confirm format` accepts the text as one format, and `label data` for a DataLabel row, truncated to 80 characters, which replaces the default data label. Characteristics other than notes are not set from the label table; the maintainer was unsure of their use, and a Char type, with the name in PropertyCode and the value in PropertyText, could be added later. VariableNote and DatasetNote rows are written directly as the characteristics that `notes` itself uses, `<var>[note1]`, `<var>[note2]` and so on, or the same on `_dta`, with the count in `[note0]`, through Mata `st_global()`. The `note` command is not used because the test log of 17 Oct 2026 showed that it turns a standalone TS into a time stamp and fails on a note that contains a lone backquote. An application that fails also counts as skipped. Label text is read with Mata `st_sdata()`; value-label and variable-label text is passed through `macval()` and note text through `st_local()`, so that `$` and backquotes in it are not expanded. Notes are applied in PropertyCode order where PropertyCode is filled in: numerically if every code among that variable's notes (or the dataset's notes) is a number, otherwise as text. Notes without a PropertyCode follow, in the order SQL Server returns them, which is not guaranteed. Zero rows means zero iterations. No do-file generation, no `file write`, no `reshape`. The time of the label step grows with the label rows alone (rewritten on 20 Oct 2026, after the benchmark showed the earlier loop, which switched frames and searched lists of every variable for each row, taking seconds on a wide table with many value-label rows; the maintainer required that what is applied, skipped and counted does not change): a Mata function, `_sqldta_lblprep`, matches each row to its variable through an associative array and makes the decisions above, and sets with one `st_vlmodify()` for each variable the ValueLabel rows that `label define` is sure to accept (a whole-number code within the range of a long, -2,147,483,647 to 2,147,483,620, and text of at most 32,000 bytes with no line break, no `"'` and no `` `" ``, which would upset the compound quotes; the range was narrowed after the test log of archive 717d9c3 showed `st_vlmodify()` taking code 2,147,483,647 without the label being found under it, so that `label define` decides on codes above it; the log of archive 0898c5a showed `label define` refusing that code with r(198)); every other row goes through the commands above, from a loop over those rows only.

**Column selection.** `sqlselect()` takes a Stata-style list of column names separated by spaces, or by commas as scripts for the predecessor wrote it, with the wildcards `*` and `?`, matched without regard to case against the columns of the table and of any linked tables, as listed by the column query described below. Each column is placed in brackets in the SQL, so T-SQL reserved words work, and is given the name as typed, so loaded names keep the user's case; a column matched by a wildcard keeps its own name. A name that matches no column is an error that names the column and the table. Expressions and aliases are not accepted. Column names must be valid Stata names (letters, digits and underscores, not starting with a digit, at most 32 characters, no spaces, not a reserved word); the help file and README state this as a requirement on the table. A column whose name is not valid is left out, and a note lists such columns; they are also in r(dropped). If no column of the table, or of its linked tables, has a valid name, sqldta stops with error 111 and says so (20 Oct 2026, after a table whose column names all start with a digit and hold spaces gave "sqlselect(): no column ... matches *" although no `sqlselect()` was given). The column query reads `[database].sys.all_columns` for the OBJECT_ID of each table, which also covers views and system views such as INFORMATION_SCHEMA.TABLES; a table with no columns there is reported as not found or not readable (error 601). Label rows for columns that exist but were not selected are not counted as skipped; only rows that name no column of the table, and applications that fail, are. The same column query supplies the date columns, replacing the separate date query. Rationale: users should not need to know SQL, and the syntax should match Stata's.

**Filtering.** The `if` qualifier takes a Stata expression, which a Mata parser at the end of sqldta.ado translates to T-SQL, so that users need not know SQL; `sqlwhere()` keeps taking T-SQL, which scripts for the predecessor pass, and both may be given. The rule is that the rows loaded are the rows a full load followed by `keep if` would leave, with one exception, documented in the help file at the maintainer's choice (20 Oct 2026): text is compared as stored, so for a char, varchar or text column not named in `unicode()`, a literal with characters outside ASCII selects rows whose loaded bytes `keep if` would not match. So a missing value is greater than every number (`x > 5` becomes `(x > 5 OR x IS NULL)`), the negation of a comparison is true where the comparison is unknown (through `CASE WHEN ... THEN 1 ELSE 0 END = 0`), a NULL string counts as `""`, string comparisons use the binary collation `Latin1_General_BIN2`, so that they are case-sensitive, a number compared with a `date` column is a Stata daily date, and a number compared with a date-time column is a Stata `%tc` value in milliseconds and with a `time` column milliseconds since midnight. Date-time and time columns are compared as the values that are loaded (see Data types): whole milliseconds, `datetime` in the steps of 1/300 s that SQL Server shows (.000, .003, .007), and `datetime2` and `datetimeoffset` before 01jan0100 missing. A comparison with a literal is rewritten as a comparison of the column itself with the bound that gives the same rows (for example `x <= L` becomes `x < L + 1 ms`, and for `datetime` the bound is the next step, written as a `datetime` literal so that the result does not depend on the compatibility level), so that an index can be used; a comparison of two such columns compares their loaded values computed in SQL, which cannot use an index; `datetimeoffset` is compared as its clock time, through `CAST(... AS datetime2(7))`. Supported: column names (exact, without regard to case, no abbreviation), numbers, `"strings"`, `.`, `== != ~= < <= > >=`, `& | ! ~`, parentheses, a unary minus, `missing()`, `inlist()`, `inrange()` with literal bounds, `substr()` with a literal start of 1 or more and a literal length or `.`, the string case and trim functions, `year()`, `month()`, `day()`, `td()`, `tc()` (the seconds, or the minutes and seconds, may be left out, and the date may be left out for a time of day, which Stata accepts too: test log of archive fc0440b) and `dofc()`. Decided 18 Oct 2026: a date compared with a date-time, `year()`, `month()` and `day()` of a date-time column, a time column compared with a date-time column, and `tC()` stop with error 198 and a message that suggests `tc()` or `dofc()`, because in Stata they compare days with milliseconds, which is almost never meant. Arithmetic and anything else stop with error 198 and a message that points to `sqlwhere()`. Columns of character types other than `text` and `ntext`, numeric types, `date`, the date-time types and `time` can be used; other types, `text` and `ntext` included, because SQL Server cannot compare them with `=` or pass them to `LOWER()`, stop with error 198. Limitations for the help file: trailing spaces are ignored in SQL Server comparisons; `substr()` counts characters, not bytes; comparisons through the binary collation cannot use an index. Mata functions defined in an ado-file are private to it, so `mata which` cannot see them (the test log of 18 Oct 2026 showed every `if` test stopping at a `mata which` check), and `clear mata` does not remove them (the next log, on Stata 19, showed `sqldta if` working after `clear mata`). `sqldta` with `if` still calls a no-op function, `_sqldta_present()`, first, and stops with error 3499 and asks for `discard` if it is missing; the help file does not mention this, since it has not been seen to happen. The `if` expression is split from the options by a Mata function (at the first comma outside parentheses and double quotes) before `syntax` runs, not by `syntax [if]`, because `syntax` checks the variables of an `if` expression against the data in memory: the test log of 18 Oct 2026 showed "num not found".

**Split tables.** A table whose columns are split across several tables is described by Link rows in the label table (see Metadata contract), one row per linked table. The key column has the same name in the main table and in every linked table, and must be a valid Stata name. Links are followed automatically whenever Link rows exist for `dataset()`, filed under its schema and name, in the order of their PropertyText, and only 1:1 links are supported, which the help file documents. Before the data load, one query per linked table checks that its key does not repeat (missing keys are ignored, since they match no row); a key that repeats stops the command with error 459 naming the table, because it would multiply rows without warning. A linked table or key that is not found stops the command with error 601 or 459. The join is done in SQL as a derived table, `SELECT ... FROM (SELECT m.*, <linked columns> FROM <main> AS m LEFT JOIN <linked> AS l1 ON l1.<key> = m.<key> ...) AS t`, so `sqlselect()`, the filter and `sqlrand()` apply to the joined table as if it were one wide table, and linked tables are not fetched in full. The linked columns come from the same column query as the main table's (see Column selection), leaving out the key; a column name that appears in more than one table is taken from the first table that has it (the main table, then linked tables in order), and a note lists the columns left out. A linked table named without a schema is in the schema of the main table; this replaced `multischema()` on 18 Oct 2026, when no label table had Link rows. Label rows filed under a linked table's own schema and name are applied as well as those of `dataset()`. Two tables that get the same rows through a view each join the linked table of their own schema, unless the Link row names `schema.table`. The join replaced the predecessor's, which loaded every linked table in full.

**Data types.** Agreed with the maintainer on 18 Oct 2026, after the type report of that day (HANDOVER.md, Discoveries), and confirmed after the passing log of archive eace2cd, including plain `%tc` for date-times and the handling of wide decimals. `odbc load` mishandles several SQL Server types, some differently with different drivers, so `sqldta` sends those columns as expressions in the select list, aliased to the name loaded, and converts them after the load in `_sqldta_convert`; `WHERE` refers to the source columns, so the `if` qualifier and `sqlwhere()` are unaffected. The column query returns the SQL type of each column (for hierarchyid, geometry and geography, which share system_type_id 240, the name of user_type_id), and its max_length, precision and scale; `_sqldta_colexpr` gives the expression. datetime, datetime2 and smalldatetime: the value of `CONVERT(varchar(23), c, 121)`, which keeps milliseconds, drops digits below them without rounding, and shows datetime in its steps of 1/300 s; values before 01jan0100 are missing. datetimeoffset: the clock time as stored, with the offset dropped (decided 18 Oct 2026), through `CAST(c AS datetime2(7))`; datetime2(3) would round, and overflow at 9999-12-31. Since 20 Oct 2026 (decided by the maintainer after the profile, on condition that the values stay exactly the same) these are sent as a number of milliseconds since 01jan1960, a float, computed without converting the value to text (decided 20 Oct 2026, after the profile at archive fb4b871 showed the first form, `CAST(CONVERT(varchar(23), c, 121) AS datetime2(3))` three times over, costing more than the text method on tables with several date-time columns; archive HANDOVER.md, section 4.12): for datetime, `DATEDIFF(day, '19600101', c) * 86400000 + (ticks * 10 + 1) / 3`, where ticks, the 1/300 s since midnight, is `CAST(SUBSTRING(CAST(c AS binary(8)), 5, 4) AS int)` and the integer division rounds each tick to the millisecond that SQL Server shows, whatever the compatibility level; for datetime2, smalldatetime and datetimeoffset, with x the column or `CAST(c AS datetime2(7))`, `DATEDIFF(day, '19600101', x) * 86400000 + DATEDIFF(millisecond, date of x, x)`, which counts whole milliseconds and so cuts the digits below them, NULL before 01jan0100 for datetime2 and datetimeoffset. The `if` translator keeps the text form for a column's loaded value, which it uses only to compare two date-time columns. Every value is a whole number below 2^53, and `DATEDIFF_BIG`, which needs SQL Server 2016, is not used. Stata sets only `%tc`. The site global `SQLDTA_DTTEXT` sends the text itself instead, converted with `clock(s, "YMDhms")`, the method before 20 Oct 2026. Either way the columns are in `r(converted)`, and `r(datetimes)` gives `number` or `text`. time: `DATEDIFF(millisecond, CAST('00:00:00' AS time), c)`, with `%tcHH:MM:SS.sss`. uniqueidentifier: `CONVERT(char(36), c)`. char, varchar and text: sent as they are (decided 20 Oct 2026, after a benchmark against the predecessor showed sqldta taking up to twice as long on large tables with many character columns, which the maintainer did not accept, and a profile confirmed that converting them to nvarchar was the cause; archive HANDOVER.md, section 4.9), so text outside ASCII arrives as the bytes of the column's code page; char and nchar through `RTRIM()`, and varchar and nvarchar keep their trailing spaces. The option `unicode(list)` names columns, with the names and wildcards of `sqlselect()` (the same parser, `_sqldta_select`) and `unicode(*)` for all, whose char, varchar and text are sent as before: `CONVERT(nvarchar(n), c)`, or `nvarchar(max)` above 4,000 characters, char through `RTRIM()` as well, and text as `CONVERT(nvarchar(max), c)`, so that text outside ASCII arrives as valid UTF-8; a name that matches no column stops with error 111, other matched columns are left as they are, and `r(unicode)` lists the columns converted. The help file gives the one-line fix for text already loaded, `replace v = ustrfrom(v, "windows-1252", 1) if ustrinvalidcnt(v) > 0`. Label text stays Unicode: the label query returns PropertyText as nvarchar(max). xml: `CONVERT(nvarchar(max), c)`, because ODBC Driver 18 skips xml. hierarchyid: `c.ToString()`. geography and geometry: `c.STAsText()`. sql_variant: `CONVERT(nvarchar(4000), c)`. binary and varbinary: `CONVERT(varchar(2n+2), c, 1)`, or varchar(max) when longer, so that short hashes are str and not strL; image through `CAST(c AS varbinary(max))`; rowversion (timestamp) as varchar(18). decimal and numeric of precision p up to 15 and scale s get `%(p+2).(s)f`, unless `nodecformat` is given. Those of precision over 15 are sent as `CONVERT(varchar(41), c)`: of scale 0 (decided 18 Oct 2026) they are treated as `bigint` is, and of a scale above 0 they become doubles through `real()`, with `%10.0g`, because the test log of archive fc0440b showed the legacy driver rounding them to about 15 significant digits (decimal(16,2) 99999999999999.99 arrived as 100000000000000), where ODBC Driver 18 gives the nearest double. Format rows are applied later and so override all these formats. `bigint` arrives as a string with both drivers (type report of 18 Oct 2026); such a column becomes numeric (stored in the smallest type that holds it, with `%20.0g` if it stays double) when every loaded value can be held exactly in a double, that is up to 2^53, and otherwise stays a string with a note. `odbc load` has a `bigintasdouble` option, but it stops with an error when a value is too large, so it is not used. The legacy "SQL Server" driver returns `date` columns as strings, and a guarded conversion (convert only when the Stata variable is a string) is kept for it, with `%td`; ODBC Driver 18 returns them as Stata dates. Types not listed are left to `odbc load`. Among them is bit, which Stata has no Boolean type for: it arrives as a byte holding 0 and 1, with NULL as missing, through ODBC Driver 18 and the legacy driver (type reports of 18 and 19 Oct 2026), and tests 169 to 179 check its values and the `if` qualifier on it (asked for by the maintainer on 19 Oct 2026).

**Documentation.** Decided 21 Oct 2026, when the maintainer asked for a README that guides the people who use the command, rather than leading with conditions, caveats and site configuration, and for the setup in a document of its own, kept on GitHub. README.md is for users: getting started with the dialog and the command, choosing columns, choosing rows with the `if` qualifier and `sqlwhere()`, a random sample, labels, what arrives in Stata, results, the settings in brief, the requirements, installation and status. docs/setup.md is for whoever installs sqldta for a site or for their own use: requirements, installing, the settings file, connecting (several templates, drivers, encryption, checking), the label table (layout, an example, the index and collation advice, split tables, a view over a label table of another layout), the menu item and the dialog, and a table of messages and remedies. docs/development.md is for whoever changes the package: the repository, `dev.do` and trying a branch while a release is installed, the tests and their fixtures, and releases. `net install` installs only the files of `src/sqldta.pkg`, so docs/ is not installed; the help file, which is installed and matches the installed version, keeps the full reference of the command's behaviour, the list of settings, the label table's layout and how its rows are applied, and a Requirements remark with the condition of a case-insensitive collation, and links to the setup guide for procedures. Tests 212 to 221 check the README's examples of `sqlwhere()` and the `if` qualifier on the generated table of admissions, `sqldta_test.sqldta_test_adm`, whose columns have the README's names.

**Collation.** sqldta supports databases with a case-insensitive collation, the default when SQL Server is installed. It matches column names without regard to case (see Labels and Column selection), which assumes that no two columns of a table differ in name only in case. Databases with a case-sensitive collation, where two columns or tables can differ in name only in case, are not supported (decided 21 Oct 2026, after the work had been on hold since 18 Oct 2026, because it would add too much complexity; the maintainer may look at it again after the first release). The help file and README state this as a condition of use, from the first release. The plan that was on hold is in archive HANDOVER.md, section 4.3.

**End of run.** `sqldta` sets the data label of the target frame to `database.schema.table`, truncated to 80 characters (the data-label limit), unless a DataLabel row replaces it, and displays one summary line: observations and variables loaded, the source as `database.schema.table` and the number of linked tables, the target frame, and, unless `labels(none)` is given, the counts of value-label sets, variable labels, display formats, variable notes and dataset notes applied and of label rows skipped, or, when the label table is not found, lacks columns of its layout or the label query fails, that no labels were applied.

**Results.** `sqldta` is rclass. It returns the scalars r(N), r(k), r(n_vallabels), r(n_varlabels), r(n_formats), r(n_varnotes), r(n_dtanotes) and r(n_skipped), and the macros r(frame), r(server), r(database), r(table) (`database.schema.table`), r(sql) (the data query), r(labels) (the words of `labels()` applied, in a fixed order; empty for `labels(none)`), r(labelstatus) (`none`, `applied`, `notfound` or `failed`), r(converted) (date-time columns, and date, bigint and wide numeric columns converted from strings), r(unicode) (the columns sent as Unicode through `unicode()`), r(datetimes) (`number`, or `text` with `SQLDTA_DTTEXT`), r(links) (linked tables as `schema.table`), r(linkkeys) (their keys), r(dropped) (columns left out, separated by commas) and r(settings) (the settings file read, or empty).

## Metadata contract

Decided 21 Oct 2026 (archive HANDOVER.md, section 4.14), when the maintainer asked for a schema column, so that tables of the same name in different schemas can have their own rows, and for column names that suit a published package, and agreed the names Claude proposed. The label table (default `ref.DataProperties`, in the same database as the data) holds one row per label item:

| Column       | Meaning                                                                                   |
|--------------|-------------------------------------------------------------------------------------------|
| TableSchema  | schema of the table or view the row applies to                                            |
| TableName    | name of that table or view; with TableSchema, matched against `dataset()`                  |
| ColumnName   | column name; empty for DatasetNote and DataLabel rows; for Link rows, the key column        |
| PropertyType | ValueLabel (value label), VariableLabel (variable label), Format (display format), VariableNote (variable note), DatasetNote (dataset note), DataLabel (data label), Link (linked table of a split table); matched without regard to case |
| PropertyCode | for ValueLabel rows: the integer code; for VariableNote and DatasetNote rows, optionally the order in which notes are applied |
| PropertyText | the label or note text; for Format rows, the format, such as `%9.2fc`; for DataLabel rows, the data label; for Link rows, the linked table as `table` (in the schema of the main table) or `schema.table` |

The rows of a table are those whose TableSchema and TableName are its schema and name, compared under the database's collation. sqldta reads only this layout; a label table without the six columns gives a note and a load without labels (see Labels). Before sqldta 0.4.0, which was not released, the layout had no schema column, so that tables of the same name in different schemas shared their rows. A site whose label table has another layout, which other software reads and which cannot be altered, reads it through a view of this layout; that view, and any table it needs, are the site's, not the package's, and docs/setup.md shows a short example. Alternatives considered and not taken: reading both layouts, a mapping table in the package's layout, and Dataset holding `schema.table`.

All columns are character types, because R and other software read the same table; so sqldta checks that a ValueLabel row's PropertyCode is an integer before applying it. Other columns, such as the DataType column that the fixture label table has, are not read; the fixture keeps DataType with a mix of values, so that the tests show they make no difference. docs/setup.md recommends an index on (TableSchema, TableName, PropertyType), and the help file points to it; the index needs those columns to be of a type with a length, such as varchar(128) or nvarchar(128), not varchar(max) or nvarchar(max); the fixture label table has it. Because sqldta compares them with `N'...'` literals, docs/setup.md also says that under a SQL collation (a name beginning `SQL_`) the index is used only if the columns are nvarchar, while under a Windows collation varchar columns can use it. Anyone with SQL Server who builds a table or view of this layout can use the package. Document the contract in docs/setup.md and in the help file.

## Coding conventions

- `tempname`, `tempvar` and `tempfile` for anything temporary; no fixed names for working frames, file handles or variables.
- Compound double quotes around any string that may contain quotes (SQL, label text, notes).
- `capture` only where the failure is expected and handled on the following line.
- Subprograms inside sqldta.ado carry a `_sqldta_` prefix, and those inside sqldta_dlg.ado a `_sqldta_dlg_` prefix.
- The help file (SMCL) is updated in the same commit as any change to options or behaviour.
- A SQL script that drops and recreates objects, such as tests/create_fixtures.sql, drops every table, view and function it creates at the top, views first, in a batch of its own ended by `GO`, before anything is created; a new object gets its drop there. SQL Server compiles a batch as a whole, so an `INSERT` or `SELECT` that names a column that a table does not have as it still exists stops the batch before a `DROP` earlier in it has run, and the maintainer then has to drop each object by hand (the maintainer's instruction of 21 Oct 2026, after the change of the fixture label table's columns).
- Each session works on its own branch and opens a pull request into main; a pull request is merged with a merge commit, only after a passing Stata log on its head. Releases are tags on main (v1.0.0 and so on), with the *! version lines and Distribution-Date bumped in the same commit, so installations update with adoupdate; other pull requests leave the Distribution-Date alone.
- A change to any fixture, or to the generator of `tests/create_fixtures.sql`, raises the fixture version in that script and `TEST_FIXVERSION` in `tests/test_sqldta.do` in the same commit.

## Working method

1. Before writing a large new part, present the proposed structure and the list of tests, and wait for approval.
2. tests/test_sqldta.do is self-contained. It reads only the objects of tests/create_fixtures.sql (hard constraint 6), fixes every setting but the server, the second server, the connection template and the database, which `tests/test_config_local.do` sets, and puts an empty settings file of its own, in a folder of `c(tmpdir)`, first on the ado-path, so that a site's `sqldta_site.cfg` does not change the tests; the tests of the settings file write their lines into it. Before test 1 it stops with a message if a file of `src/sqldta.pkg` is not found in the clone's `src/`, or if the fixtures are not of the version it expects. Each test runs under `capture noisily` so one failure does not stop the run, uses `assert`, and the file ends with a single line `SQLDTA TESTS: <n> passed, <m> failed` followed by the names of failed tests. Before test 204, a type report, which asserts nothing and is not counted, shows the server's version, compatibility level and collation, then loads each column of the data-type fixture tables on its own, through the connection template and through the DSN, and shows its storage type, display format and values, then loads each whole table with `describe`, so that decisions on types can rest on a log. After the last test, the data-type fixture tables and the known table are left loaded in frames, in order of id, for comparison with SSMS in the Data Editor. The test of `clear mata` stays last, because it clears the file's own Mata functions. The file writes its log to tests/test_sqldta.log, which git ignores.
3. After a pasted log: check that its branch and commit lines match the pushed head, fix what failed, state exactly what changed, and wait for the next log. Do not assume a fix worked.
4. When a design decision changes in conversation, update this file in the same commit.
5. Commit messages are one line in the present tense.
6. Code reaches the maintainer's Stata by push and pull, not by file transfer. The maintainer keeps a clone and works on it with RStudio's Git pane: the branch list switches to the session branch, and Pull brings it up to date. The maintainer prefers not to use the git command line, so instructions to the maintainer are given in terms of RStudio's Git pane and GitHub's web pages where they can do the job, and as exact commands for RStudio's Terminal where a git command is needed. Stata runs on a machine without git, from the root of the clone, with the installed release untouched: `do tests/test_sqldta.do` in a new Stata window for the tests, and `do dev` to try a branch in a session, `do dev release` to switch it back. A branch is never installed (docs/development.md). The test log shows the branch and commit, read from .git.
7. Each session starts its own branch from main and opens a pull request into main, which is merged with a merge commit, so that every commit cited in the records stays in main's history. Work after a merge belongs in a new session.
8. At the start of a session, read HANDOVER.md as well as this file. Keep it current: update it in the same commit as any change it describes, and before a session ends, with what was done, what the logs showed, what was decided and what is still open. Settled design belongs here; process, evidence, plans not yet built and open questions belong there.
